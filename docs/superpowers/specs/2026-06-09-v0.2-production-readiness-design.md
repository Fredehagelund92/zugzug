# v0.2 — Production-readiness (design)

**Date:** 2026-06-09
**Target release:** v0.2.0 (4-6 weeks)
**Status:** Locked. Ready for implementation plan.

---

## Goal

Round out v0.1's rough edges so serious self-hosters can run Zugzug in production without surprises. Three cohesive epics plus small polish: scheduler hardening, role-based permissions, and completion of Snowflake authentication. No new user-facing features; this release is about reliability, access control, and operational visibility.

## Non-goals (deferred to v0.3+)

- Per-dimension permission scoping (v0.2 ships flat role-based control only)
- Approver-only role (separate from editor)
- Realtime presence / activity feed (E1 epic — separate release)
- AI-assisted curation (#3-5)
- Multi-tenant UI surface (gated behind hosted-offering decision)
- Bulk operations in Triage (#33)
- CSV import/export (#34 — Parquet covers v0.1)
- Unified search (#35)

## Epic A — Scheduler hardening

Closes epic #15. All 10 sub-issues land in v0.2 as one cohesive PR.

### Issues + planned order

| Issue | Type | Note |
|---|---|---|
| #10 — Extract scheduler to `server/src/scheduler.ts` | Refactor | Do first; gives clean module to build on. |
| #11 — `anyScanDue` ignores newly-registered sources | Bug | Small, do alongside refactor. |
| #7 — Persist every scan in a `scan_run` table | Schema + emission | Drizzle migration; new table holds `id`, `source_id`, `started_at`, `ended_at`, `status` (ok/error/timeout), `rows_scanned`, `duration_ms`, `error_message`. |
| #14 — Persist per-source scan duration | Schema | Same migration as #7 — `duration_ms` column covers it. |
| #13 — Decouple `autoStageExactMatches` + auto-commit from `scanSources` | Refactor | Each is a separate scheduler tick concern; current coupling makes drift hard to attribute. |
| #12 — Scheduler drift and overlap logging | Observability | After decoupling, log per-tick: scheduled time vs actual time, missed ticks, overlap detection. |
| #8 — Surface scan failures in Audit feed | Observability | Emit a new audit event type on scan failure (links to `scan_run.id`). |
| #9 — Graceful shutdown drains in-flight scan | Reliability | SIGTERM handler waits up to N seconds for in-flight scan to finish or cancel cleanly. |
| #6 — Drop legacy `dimension_source.schedule` column | Cleanup | Last step. Confirm no readers remain. |

### Architecture

- New file: `server/src/scheduler.ts`. Currently scheduler logic is inline in `bootstrap.ts` / `server.ts`. Extract to a single module that exposes `start()`, `stop(drainTimeoutMs)`, and accepts a `TenantContext` / DB pool.
- `scan_run` table is **append-only** — never updated after `ended_at` is set. Powers operational dashboards and the new audit feed entries.
- Decoupling pattern: scheduler tick orchestrates a sequence of independent jobs (`scanSources`, `autoStageExactMatches`, `autoCommit`). Each job logs its own scan_run row. Failures don't cascade.

### Verification gate

- All 10 issues closed.
- `scan_run` rows visible in Dashboard for the last N ticks.
- Audit feed shows scan failures (manual: trigger one by pointing at a bad MotherDuck token).
- `SIGTERM` against a running server with in-flight scan completes cleanly in ≤30s.
- `dimension_source.schedule` column gone; no code references it.

## Epic B — Role-based permissions (RBAC)

Closes epic #36 (4 of 5 sub-issues; #30 superseded by OIDC and closes separately).

### Roles

| Role | Read | Curate (drafts) | Commit | Manage team | Manage adapters |
|---|---|---|---|---|---|
| **admin** | ✓ | ✓ | ✓ | ✓ | ✓ |
| **editor** (default) | ✓ | ✓ | ✓ | – | – |
| **viewer** | ✓ | – | – | – | – |

First user (first-signup OR first-OIDC-login) is admin. Subsequent users default to editor. Admin can change anyone's role via Settings → Team.

### Issues

| Issue | Scope |
|---|---|
| #28 — Add `role` column to `users` (admin/editor/viewer) | Drizzle migration; backfill all existing users to `admin` (so the v0.1 → v0.2 upgrade doesn't lock anyone out). |
| #29 — Server: `canMutate()` helper + gate all mutations | New helper in `server/src/auth.ts`. Every mutation handler (POST/PUT/DELETE) calls `canMutate(user.role, operation)` and returns 403 if disallowed. |
| #31 — UI: disable edit affordances + show 'read-only' badge for viewers | Component-level: `useCurrentUser().role === 'viewer'` flips writes to read-only. Show a small badge in the topbar. |
| #32 — Settings: Team section with role picker (admin only) | Add to existing Settings page. Lists members; admin can change roles. |
| #30 — Parse Google `hd` JWT claim + first-login role assignment | **CLOSE** — superseded by generic OIDC support. First-login role assignment is now in the password/OIDC handlers from PR #86. |

### Architecture

- **Server**: `canMutate(role: 'admin'|'editor'|'viewer', op: 'curate'|'commit'|'manage_team'|'manage_adapter')` returns boolean. Composed of a static permission matrix (matches the table above). Every mutation handler imports and calls it at the top.
- **Frontend**: `useCurrentUser()` returns `{id, name, email, initials, role}`. The `role` field flows from `GET /api/auth/me` (extend to include `role`). UI uses `role === 'viewer'` checks at component level — don't try to centralize.
- **Defaults**: new user → editor. v0.2 upgrade migration: every existing user → admin. This is intentional — the small group on v0.1 today is operating as admins by definition.

### Verification gate

- Schema change + backfill applied cleanly.
- A viewer logged in via API token cannot POST/PUT/DELETE anywhere; gets 403.
- Settings page shows team members with role picker; admin can demote/promote.
- Editor cannot see Settings → Team (it's admin-only).
- Test coverage: per-role permission tests for the canMutate matrix; UI tests for viewer-mode disable behavior.

## Epic C — Snowflake auth completion

No existing issues yet; file these at v0.2 kickoff. The Snowflake adapter currently supports only key-pair (`SNOWFLAKE_JWT`). v0.1's README explicitly notes this. v0.2 adds the other two modes the snowflake-sdk supports.

### Modes to add

| Mode | Use case |
|---|---|
| **Password** | Username + password. Simplest for environments without IAM/SSO. |
| **External-browser SSO** | Opens the user's browser to authenticate against their org's IdP (Okta, Azure AD, etc.). The credential prompt happens once per session; Zugzug stores a session token. |

(Key-pair stays. OAuth bearer-token + private-key with passphrase are v0.3+.)

### Architecture

- Extend `SnowflakeCredentials` Zod schema to include a `authMode` discriminator: `key-pair` | `password` | `external-browser`.
- `sdk-wrapper.ts` already constructs the connection config; route through the new discriminator and set `authenticator` + extra fields per mode.
- Settings UI: existing Snowflake credential form already has fields; add a dropdown for `authMode` and conditionally show/hide the per-mode inputs.

### Verification gate

- Connect against a real Snowflake account in each of the three modes (key-pair, password, external-browser).
- Settings UI guides the user through each mode's required fields.
- Error messages are specific per mode (e.g., "Password authentication failed" vs "Browser authentication cancelled").

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Scheduler refactor (#10) breaks existing scan timing in subtle ways | Medium | TDD with snapshot tests of current behavior before refactoring; cover the bug fix (#11) explicitly. |
| RBAC migration backfills all users to admin — surprising for a team that wanted to demote some | Low | Documented in release notes. Trivial to demote post-upgrade via Settings. |
| Snowflake external-browser mode requires real Snowflake org with SSO configured for testing | High | First confirm with one inbound user that they want SSO. If no one asks, ship password-only and defer SSO. |
| 4-6 week target slips because production-readiness work always uncovers more issues | Medium | If scope grows past 6 weeks, cut to: scheduler hardening + RBAC only; ship Snowflake auth + polish in v0.3. |
