01How it works

Four steps. No new pipeline.

Zugzug runs inside the warehouse you already have. It reads the raw tables your ELT already loaded, decides who Acme is, and writes the answer back as a real SQL table. No data leaves. No platform team required.

Define

Describe your entities — customer, product, location — in zugzug.yaml. Version-control it like any other config.

Point

Tell Zugzug which warehouse tables are which. raw.salesforce.account, raw.hubspot.companies — whatever Fivetran or your dbt models already produced.

Reconcile

Match, merge, and apply your survivorship rules — all computed as warehouse SQL. What rules can't decide goes to a steward queue.

Query

Your dbt models join analytics.golden.customer like any other table. Looker, Hex, Mode — everything just works.

02Define your model

One yaml file. One warehouse table per entity.

You describe what a customer is, which warehouse tables it lives in, and who wins when sources disagree. Zugzug compiles that into SQL, runs it in your warehouse, and writes the result back as a materialized table.

zugzug.yaml
# Where the raw data already lives — your ELT put it there
warehouse: snowflake
sources:
  salesforce: raw.salesforce.account
  hubspot:    raw.hubspot.companies
  netsuite:   raw.netsuite.customer

# What a customer is in our world
entity: customer
key:    [duns, vat_id, normalized_name]

fields:
  legal_name:
    winner: most_recent_confirmed
    prefer: [salesforce, hubspot]

  primary_email:
    winner:   majority_match
    validate: [deliverable]

  headquarters:
    winner:   defer_to_steward
    fallback: freshest

  annual_revenue:
    from: netsuite   # single source of truth

match:
  strong: [duns, vat_id]            # auto-merge
  fuzzy:  [normalized_name, hq]    # ≥ 0.85 → queue
  block:  [country]                # never cross

publish:
  table: analytics.golden.customer   # written back here
  grant: [dbt_role, looker_role]

04The steward UI is optional

For the 1% rules can't decide.

When two sources disagree and no rule covers it, Zugzug parks the conflict in a queue. A non-technical steward — sales ops, finance, a data-savvy PM — clears them one at a time.

The queue is just a thin React app reading queue items from your warehouse and writing the steward's decisions back to it. Host it on a subdomain, embed it in your internal tools portal, or skip it entirely if rules already cover everything.

Not bundled. Install with zugzug ui.

05Architecture

Three layers. The data never leaves.

06Three things we won't budge on

The boring middle is the whole point.

01

Your warehouse, not ours.

Zugzug doesn't move your data, doesn't host it, doesn't see it. Compute and storage stay where they already are. The Zugzug process only holds metadata and the steward queue.

02

YAML is the source of truth.

No clicking through a UI to define your data model. Every entity, rule, and source mapping lives in version-controlled config. The UI is a view, never the canon.

03

The output is a table.

You shouldn't have to learn a new API to use your master data. SELECT * FROM analytics.golden.customer in your warehouse is the API. Everything else is a bonus.

07Get started

Pick your poison.

· Local · 60 seconds

$ brew install zugzug
$ zugzug connect duckdb ./demo.duckdb
$ zugzug init --entity customer --sample
$ zugzug reconcile

Try it against the bundled sample data in DuckDB. Zero credentials, zero cloud cost.

· Your warehouse

$ zugzug connect snowflake \
  --account acme.us-east-1
$ zugzug introspect raw.salesforce.*
$ zugzug reconcile --dry-run

Read-only first. --dry-run shows you the SQL it would run and the table it would create — nothing executes until you say so.

· In production

$ docker run zugzug/zugzug \
  reconcile --every 15m
# or wire into your dbt run:
$ dbt run-operation zugzug

One container on a tiny VM, or invoked from your existing dbt schedule. No new orchestrator to learn.
